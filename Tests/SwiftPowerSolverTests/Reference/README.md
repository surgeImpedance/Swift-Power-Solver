# pandapower reference dumps

Generated by `Tools/dump_reference.py` with any Python that has
[pandapower](https://www.pandapower.org) installed:

    python Tools/dump_reference.py

Each JSON holds, for one IEEE case, full precision:
ppc-level bus/branch/gen parameters (already per-unit), pandapower's own Ybus
as sparse triplets, and the solved bus voltages/angles + branch flows —
with and without generator Q-limit enforcement.

The Swift tests diff `YbusBuilder` / `NewtonRaphsonSolver` output against
these files. They are checked in so `swift test` works from a bare clone
with no Python installed; regenerate only when changing the dump script or
bumping pandapower.

## `zip.json` — the ZIP (voltage-dependent load) oracle (D80 step 3, 2026-09-02)

Generated by `python Tools/dump_reference.py zip` — an ADDITIVE file, never a
re-emission of `case14/39/118.json` (their bytes are on the critical path of
four gates). For each case: the coefficient vector (P = 0.3 Z + 0.3 I + 0.4 P,
Q = 0.5 Z + 0.3 I + 0.2 Q, applied uniformly to every load; one load per bus
asserted because pandapower count-averages otherwise), the pinned options
(`max_iteration=60` is required — pandapower's partial Newton needs 13
iterations on case39), `pandapower_version`, the ZIP solutions with and
without Q-limits (`dump_solution` shape plus `consumed_load` = pandapower's
`res_load`), and the CONSTANT-POWER solution re-solved in the same run.
`ZIPReferenceTests` asserts, non-droppably: nontrivial coefficients;
max|Vm_zip − Vm_pq| > 1e-6 on every case and setting; and the in-file
constant-power block equals the committed case fixture bit-for-bit (the
regeneration control). `iterations` in the zip blocks is pandapower's
partial-Newton count — provenance, never a gate; MATPOWER's full-Newton count
is the comparable one (substation-lab `docs/investigations/zip-oracle-control.md`).
